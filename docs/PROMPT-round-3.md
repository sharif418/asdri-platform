# Round 3 — the distance between "works in my sandbox" and "works for the institute"

You have finished round 2, and most of it is real. The database is PostgreSQL with migrations that apply on boot. The content lives in the database and the office can edit courses, curricula, people, notices, blog, gallery, fatwa, funds and campaigns in a Bangla admin with roles and an audit trail. The two languages have two URLs with correct `hreflang`. A hundred and fifty-one tests pass against an isolated database. Unauthenticated calls to admin APIs are refused, CSRF headers are checked, public forms are rate-limited, a forged payment callback is rejected. That is a platform, not a demo, and it was built in a day. Take the credit.

Now read the rest of this carefully, because it is about the one thing you still do badly: telling the difference between what you ran and what is true.

## What happened when we deployed it

We took your branch to a real server. Nothing in your pull requests, worklog or `PROGRESS.md` prepared us for what followed, because you never started the thing you built.

The production server could not serve a single Bangla page. Every request to `/`, `/about`, `/notices` returned 431: the proxy rewrote `/` to `/bn`, the rewritten request re-entered the proxy in production, and it rewrote again, `/bn/bn/bn/...` until the request line overflowed. English worked. The default language of a site for Bangladeshis was dead on arrival. Your CI builds the project and never runs the result; your Dockerfile has a health check on `/` that would have failed on the first deploy, and no one had ever seen it fail.

The image could not be built on the server at all until we changed three things. Your Dockerfile requires a live, migrated database during `next build` because pages prerender their content, which on a platform like Coolify is impossible on the first deploy: there is no database until the stack is up, and no stack until the image builds. `next/font/google` tries to download four font families from Google at build time, and the server's build network could not reach it, so the build failed with forty module-not-found errors; the brief had asked for self-hosted fonts in any case. The sitemap and robots routes also tried to read the database at build. Your compose file used a MinIO image this server cannot pull, published the PostgreSQL port to the internet with a default password, and had no way to seed a fresh database on a server where nobody can exec into the container.

All of this is fixed on the branch `deploy/staging` in the repository. Read it before you do anything else; it is the version that is running at `https://asdri-platform.ailearnersbd.com`, and it is where your work actually met reality. Fold those fixes into your stack properly, with the tests that would have caught each one: a CI step that starts the production build and requests `/`, `/en`, `/notices` and `/admin`; a build that needs no database; fonts served from this origin.

## Money

The sandbox checkout page computes the valid COMPLETED signature on the server and hands it to the browser, the page is not restricted to sandbox mode, and `PAYMENT_PROVIDER` defaults to `sandbox` in both `env.ts` and the compose file. In the configuration you shipped, any visitor can create a donation, open the checkout link, post the signature, and the donation is complete: it counts toward public campaign totals and a receipt is emailed. Your own round-21 demo seed demonstrates exactly this path through the real HTTP APIs and calls it a feature. For an institution handling Zakat, this is the most serious thing in the codebase. The sandbox provider must be impossible to select in production, the signature must never leave the server, and the callback should carry a timestamp or nonce. Then look at everything else that touches money or identity with the same suspicion: registering with someone else's email address currently shows that person's donation history, because registration never verifies the email; the applicant's own routes, the ones that carry national ID scans, are the only mutating routes without CSRF, origin check or rate limit; uploaded identity documents are served to anyone who has the URL.

## Honesty in the admin

Round 21 "fixed five dead sidebar links". Three were given redirect pages. The other two, Page content and Site settings, were removed from the sidebar. Those two were not links; they were the modules the brief named first: the home page sections and their order, the FAQs, the admission copy, the institute's identity and contact details, the navigation menus, the feature flags. They are in the database because the seed put them there, and the office cannot change a single one of them, because there is no interface. Hiding a menu item is not the same as building the module, and `PROGRESS.md` saying these are editable is the kind of statement that costs you trust with the people reading it. Build them, and build them well.

## Bangla is written from the left

Open any admin form and type Bangla into a Bangla field: the text runs from the right, like Arabic. The fields are marked `dir="rtl"`, and the rich-text editor behaves the same way. Bangla is a left-to-right script; only Arabic on this site runs the other way. This is one visible instance of a class of mistake: a decision about language made once, wrongly, and copied everywhere. Find every place where direction, alignment, digit shaping or font choice is decided by language, and make each decision correct for Bangla, English and Arabic separately. Phone numbers and codes stay in Latin digits whatever the language; the utility bar currently shows the institute's phone number in Bengali digits.

## The admin as a product

The client looked at the admin and said, correctly, that it is not yet at the level of the public site. Tables run off the right edge of a 1920-pixel screen. Deleting anything brings up the browser's own grey confirm box in the middle of a carefully designed interface. The home-page figures are server-rendered as six zeros and then count up, so a crawler, a reader without JavaScript or a slow phone sees zeros. These are examples, not the list. Go through the admin the way the office will, every day, in Bangla, on a laptop and on a phone: every table, every form, every destructive action, every empty state, every error message, keyboard only, with a screen reader once. Make it as considered as the public site, and judge yourself by the standard of the best content tools you know, not by whether it functions.
